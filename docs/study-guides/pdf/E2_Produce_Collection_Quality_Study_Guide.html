1. Epic overview

Epic 2 covers the physical journey of produce into the centre: the farmer books a delivery, the officer registers the delivery and weighs it, the inspector grades it and records accepted / rejected quantities, the system generates a batch code for accepted produce and a numbered collection receipt for the farmer.

Stakeholders: Farmer, Collection Centre Officer, Quality Inspector.

2. Core concepts

2.1 The collection life-cycle (state machine)

Appointment: scheduled → confirmed → arrived → completed (also: cancelled, no_show) Collection: scheduled → arrived → weighed → pending_inspection → under_inspection → accepted | partially_accepted | rejected → added_to_inventory → payment_pending → completed

A state machine means each status can only move to certain next statuses (a transition table in the controller). Trying anything else returns 409 Conflict, for example "Collection cannot move from scheduled to accepted". This prevents skipping weighing or inspection.

2.2 Appointments vs walk-ins

  • A scheduled delivery links the collection to an appointment (appointment_id); the appointment becomes completed automatically when the inspection is finalised.
  • A walk-in is a collection with no appointment – the officer registers it directly. Both end up as the same kind of collection record, so everything after (weighing, inspection, payment) is identical.
  • Capacity: each centre accepts a maximum number of appointments per day (system setting, default 60), so queues stay manageable.

2.3 Net weight is calculated, never typed

net_weight_kg = gross_weight_kg − container_weight_kg is a PostgreSQL generated column (GENERATED ALWAYS AS … STORED). Nobody – not the API, not the UI – can write a wrong net weight; the database computes it from the two inputs. This is a strong answer for "how do you avoid manual calculation errors?".

2.4 One transaction for inspection – finalize_inspection()

When the inspector submits, a single PostgreSQL function does everything atomically (all or nothing):

  1. Validates the collection state and the quantities (see section 3.4).
  2. Inserts the quality_inspections row and one collection_rejections row per rejection reason.
  3. Sets the collection status: rejected (grade rejected), partially_accepted (some rejected), or accepted.
  4. Marks the linked appointment completed.
  5. If accepted quantity > 0: generates a batch number (generate_batch_no()), looks up the current price, computes the expiry date from the crop's shelf-life days, creates the inventory_batches row (QR value HH-<batch_no>) and a "received" ledger entry in inventory_transactions.
  6. Creates the numbered collection receipt (RCT-YYYY-000001 style via next_receipt_no()) and notifies the farmer.
Why a database function? If the server crashed half-way in plain code you could have an inspection without a batch or a batch without a receipt. In one transaction either everything is saved or nothing is.

2.5 Traceability (E2-US7)

The batch stores collection_id, farmer_id, crop, grade and expiry. Later, orders allocate stock from batches, so any sold kilo can be traced back to the farmer and the delivery day: farmer → collection → inspection → batch → order → invoice.

2.6 Receipts and farmer confirmation (E2-US8)

  • Receipt number format RCT-<year>-<6-digit sequence>, unique per collection (one receipt per collection).
  • The farmer sees the receipt, can print / save as PDF, and either confirm it or dispute it (a note explaining the problem is mandatory when disputing). The officer is notified of disputes.
  • Receipt status: issued → confirmed | disputed.

4. Suggested live demo

  1. Farmer logs in → Schedule delivery. Try tomorrow-minus-one date and a negative quantity to show the rules; then a valid booking (US1).
  2. Officer opens Delivery appointments, confirms the appointment, then Register collection linking it (US2). Show that a walk-in works without an appointment.
  3. Weigh produce: try container ≥ gross → error; then valid values and show the net weight appear (US3).
  4. Inspector → Pending inspections → inspect: choose grade, enter accepted + rejected that do not equal net weight → refused; then correct values with a rejection reason and photos (US4, US5, US6, US9).
  5. Show the success message with the new batch number and receipt number; open inventory to see the batch (US7).
  6. Farmer opens My collections → receipt → Confirm (or dispute with a note) (US8).

5. Likely viva questions and model answers

Q1. How do you make sure the net weight is correct?

It is a generated column in PostgreSQL: gross minus container. Users only enter gross and container, and a CHECK constraint plus API validation ensure gross is greater than container.

Q2. What prevents an inspector from accepting more than was delivered?

finalize_inspection() requires accepted + rejected to equal the recorded net weight; otherwise it raises INVALID_QTY (HTTP 400). The inspection form enforces the same rule.

Q3. Why is inspection implemented as a database function?

It must create the inspection, rejections, batch, inventory ledger entry, receipt and status updates atomically. A single transaction guarantees there are never partial records.

Q4. What happens if two inspectors inspect the same collection?

The second call fails with INVALID_STATE "an inspection already exists" (409); the receipt table also has a UNIQUE collection_id.

Q5. How is the batch code created and what is it used for?

A database sequence function creates the batch number; the QR value is HH-<batch_no>. It links stock to the farmer and collection for traceability and drives expiry tracking.

Q6. How is the expiry date decided?

Each crop category has shelf_life_days (default 7; longer for rice, spices, tea). Expiry = today + shelf life when the batch is created.

Q7. What is the difference between a scheduled delivery and a walk-in?

A scheduled delivery references an appointment; a walk-in does not. Both create the same collection record afterwards.

Q8. How do you prevent overbooking?

The appointment API counts bookings for the centre and date against the daily capacity setting and returns 409 when full; it also blocks duplicate bookings by the same farmer.

Q9. Why do you use status transition tables?

To forbid impossible jumps (e.g. accepting before weighing). Every status change is checked against allowed next states and returns 409 otherwise.

Q10. Can the officer edit weights later?

Only while the collection has not been inspected. After that the API returns 409, so stored quantities cannot be changed behind an approved inspection.

Q11. What does the farmer get after inspection?

A numbered receipt (accepted / rejected kg, grade, batch number), an in-app notification (and email if SMTP is on), and the right to confirm or dispute it.

Q12. How are rejection reasons recorded?

One row per reason in collection_rejections with quantity and notes; at least one reason is mandatory when anything is rejected, and their quantities cannot exceed the rejected total.

Q13. What are the roles for each action?

Farmer books and confirms receipts; officer registers, weighs and issues receipts; inspector grades; the API uses requireRole so any other role gets 403.

6. Know your limitations

  • There is no integration with a physical weighing scale – weights are entered manually (the Sprint 0 document allows a software simulator).
  • The batch QR is stored as text (HH-<batch_no>); a scannable image/camera scan is not built.
  • Evidence images are limited by the 10 MB request size of the API; very large photos should be compressed first.
  • Automated tests do not yet cover the inspection function end to end; it was checked manually (the SQL test scripts in supabase/tests/ cover stock reservation, wastage and payments).

8. Appendix – system foundations (same in every guide)

8.1 Architecture in one picture

Browser (React 18 + Vite + Tailwind + TanStack Query + react-hook-form + Zod) | HTTPS, JSON, header Authorization: Bearer <JWT> v Express REST API (Node.js + TypeScript) helmet · CORS · rate limit · authenticate · requireRole · validate(Zod) · controller · errorHandler | supabase-js (service-role key, server side only) v Supabase: PostgreSQL (tables, constraints, RPC functions, triggers) · Auth · Storage (private buckets)

Layered design: presentation (React pages) → API/business layer (Express controllers and services) → data layer (Supabase/PostgreSQL). Business rules that must never be bypassed (stock, weights, payments) are enforced in the database through PostgreSQL functions, so even a buggy client cannot break them.

8.2 Authentication vs authorisation

ConceptWhat it answersHow HarvestHub does it
Authentication"Who are you?"Email + password are checked by Supabase Auth. On success the API returns a JWT access token and a refresh token. The frontend stores them and the Axios interceptor adds Authorization: Bearer <token> to every request; on a 401 it tries the refresh token once, otherwise logs the user out.
Authorisation (RBAC)"What may you do?"authenticate middleware verifies the token with Supabase, loads the user's profiles row (role, account_status) and rejects suspended / inactive / pending accounts. requireRole(...) then allows only listed roles (administrator is a superuser). Wrong role → 403.
Ownership checks"Is this YOUR record?"Role alone is not enough: a farmer must not read another farmer's data. Controllers call helpers such as assertFarmerAccess / assertBuyerAccess (services/access.ts) → 403 if the record belongs to someone else.
Row Level Security (RLS)DB-level safety netPolicies are enabled on tables in Supabase. The API itself uses the service-role key, so the API-layer checks above are the primary control; RLS protects direct database access.

The nine roles are: farmer, collection_centre_officer, quality_inspector, inventory_manager, buyer, finance_officer, transport_coordinator, manager, administrator. Only farmer and buyer can self-register; staff accounts are created by an administrator.

8.5 Cross-cutting security measures

  • helmet security headers; CORS restricted to the configured frontend origin in production.
  • Rate limiting with express-rate-limit (general API and a stricter limit on /api/auth).
  • Safe search: user search text is stripped of characters that could alter a PostgREST filter (, ( ) % * \) and limited to 60 characters.
  • Mass-assignment protection: update endpoints copy only a whitelist of columns (a farmer cannot set their own verification status).
  • Generic login error ("Invalid email or password") so attackers cannot discover which emails exist.
  • Secrets only in .env (service-role key never reaches the browser); private storage buckets with short-lived signed URLs for documents.
  • Notifications and audit: important actions create in-app notification rows (and emails when SMTP is configured); auction awards and rejections are written to the audit log.
