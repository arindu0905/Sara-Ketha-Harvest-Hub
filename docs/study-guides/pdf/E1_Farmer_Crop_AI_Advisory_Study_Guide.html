1. Epic overview

Epic 1 manages who the farmers are and what they grow: self-registration, officer-assisted registration, verification, profiles and documents, crop registration and history, multilingual (English / Sinhala / Tamil) use, and the conversational crop-advisory assistant that recommends crops with suitability scores and reasons.

Stakeholders: Farmer (primary), Collection Centre Officer (primary), Agricultural Officers (secondary – advisory accuracy).

2.2 Farmer verification life-cycle (E1-US4)

Register ──► verification_status = PENDING (profile account_status = pending → LOGIN BLOCKED, HTTP 403) │ Officer reviews identity details + documents │ ┌────────────────┴─────────────────┐ VERIFIED REJECTED profile → active profile → inactive farmer can log in, farmer cannot log in book deliveries, add crops (message: contact the centre) notification: "Registration approved" notification with the officer's note

Why it exists: only verified farmers may use collection services and receive payments, which protects the centre from fake or duplicate farmers. Verification stores verified_by and verified_at (accountability).

2.3 Farmer–user link

A farmers row has profile_id (UNIQUE, references profiles). That one column connects a login to farmer data. GET /api/farmers/me finds the logged-in farmer through it, and ownership checks compare it with the record being accessed.

2.4 Codes, masking and uniqueness

  • Farmer code (e.g. FRM-…) is generated by the database function generate_farmer_code – unique, human friendly, never typed by users.
  • NIC is UNIQUE in the database (and pre-checked by the API → 409 "A farmer with this NIC number already exists").
  • Bank account masking: only ****1234 (last four digits) is stored in account_number_masked; the full number is not kept.

2.5 Multilingual support (E1-US2)

  • LanguageContext holds the current language (en | si | ta). The choice is saved in localStorage (hh_language) so it survives reloads, and the page language attribute and a body CSS class are updated (for the correct Sinhala / Tamil fonts).
  • Components call t(key). If a key is missing in Sinhala/Tamil it falls back to English so the UI never shows blank text.
  • Roles have translated labels (role_farmer …) and dates are formatted with the si-LK / ta-LK locale.
  • The crop advisor receives the language (lang) and answers in it; crop names are returned in all three languages.

2.6 The crop advisor (E1-US9 / US10 / US11) – how the "AI" really works

The assistant is a conversation that asks three questions, then calls POST /api/bot/recommend:

  1. Location – which district (the 26 districts / areas offered in the three languages, with search and agro-zone filter).
  2. Previous crop – quick buttons or free text (names in English / Sinhala / Tamil are normalised).
  3. Soil – acidic / slightly acidic / neutral / alkaline, an exact pH (3–10), or "I don't know".

Environmental conditions (rainfall, climate zone, altitude, soil types) come from a built-in district profile for the chosen district.

Scoring model (0–100) – transparent, not random

FactorMaxHow it is computed
Location fit40Expert-recommended crop for this district after the previous crop: rank 1 = 40, rank 2 = 36, rank 3 = 32; a primary crop of the district = 28; otherwise 8.
Crop rotation30Same crop as last season = 0 (warning); listed "avoid after" = 0; same crop family = 4; no history = 18; a legume after a non-legume = 30 (restores nitrogen); a different family = 24.
Soil pH15Full marks inside the crop's preferred pH range, falling linearly to 0 at 1.5 pH units outside. pH not given → neutral 9.
Rainfall15District annual rainfall (mid-point) versus the crop's tolerated range; falls to 0 at 1000 mm outside. Unknown → neutral 8.
  • Score = location + rotation + soil pH + rainfall, rounded. Every crop is scored (17 crops with known pH, rainfall and family data) and the top 3 are returned.
  • Rotation violations are never recommended (same crop, same family, "avoid after" list) – they are filtered out before ranking.
  • The response includes score_breakdown (points + a note per factor), so the farmer sees why a crop scored as it did (US11 "scores and reasons").
  • Gemini (optional): if a GEMINI_API_KEY is configured, the Gemini model only phrases the explanation in the farmer's language. It does not choose the crops or the scores. Without a key the built-in multilingual rationale is used (ai_source: "fallback").
Be honest about the proposal: the Sprint 0 document mentions a Java ML / Weka Random Forest. The delivered advisor uses an expert-rule scoring model written in TypeScript (plus optional Gemini for wording). A trained Java model prototype exists in the ml-service/ folder but is not what the live bot calls. Explain it as: "we chose a transparent, explainable scoring model because farmers need reasons, and it works without training data".

Worked example (illustrative numbers)

Farmer in a dry-zone district grew Rice, soil pH 6.0. For Cowpea: location 36 (rank 2 recommended) + rotation 30 (legume after cereal) + pH 15 (inside range) + rainfall 15 (inside tolerated range) = 96/100. For Rice again: rotation = 0 with a warning, so it is excluded from the recommendations.

3.4 Profile update – E1-US5

  • Ownership: a farmer can update only their own record – otherwise 403 "You can only update your own farmer profile".
  • Whitelist (mass-assignment protection): a farmer may change only: full name, email, phone, address, district, divisional secretariat, farm name/location/size, bank details, emergency contact, preferred language. Staff may additionally change NIC, assigned centre and notes. Verification status can never be changed through this endpoint.
  • Optional fields use the same NIC / phone formats; blank or null values do not overwrite existing data.
  • Bank account number is converted to ****last4 before saving. On the profile screen the field is labelled New account number (blank = keep the current one) and accepts digits only.
  • Emergency contact phone and bank account follow the same formats as in registration. Duplicate NIC while editing returns 409 "A farmer with this NIC number already exists".
  • Frontend shows inline messages as the user types (validatePhone, validateNIC).

3.7 Search and filter – E1-US8

  • Search matches name, farmer code, NIC or phone (case-insensitive), plus filters for district, verification status, centre and account status; results are paginated (limit maximum 100, page at least 1).
  • Injection protection: the text is passed through safeSearch(), which strips , ( ) % * \ and cuts it to 60 characters. Without this, a crafted search string could change the structure of the PostgREST .or() filter.
  • A logged-in farmer calling this endpoint sees only their own record.

4. Suggested live demo (5–7 minutes)

  1. Open the landing page → switch language to Sinhala/Tamil (US2). Show it stays after refresh.
  2. Register a new farmer. Try a weak password to show validation messages (US1). Submit a valid one.
  3. Try to log in immediately → blocked "pending verification" (shows US4 rule).
  4. Log in as officer → Farmer Verification → open the new farmer, check details and documents, Approve (US4). Show the farmer notification.
  5. As officer open Register Farmer: enter a wrong NIC / phone to show validation, then a valid one (US3). Re-enter the same NIC → duplicate error.
  6. Use Farmer Directory: search by name / NIC, filter by status and district (US8).
  7. Log in as the farmer → Profile: edit phone with a bad value, then a good one; upload a document (US5).
  8. Register crop, then My crops for the history (US6, US7).
  9. Open the Crop Advisor: district → previous crop → soil; show the three results, the scores and the breakdown (US9–US11); switch language and ask again.

5. Likely viva questions and model answers

Q1. Why can a farmer not log in right after registering?

Because registration creates the farmer in pending state. A collection officer must verify identity first (US4). This stops fake farmers receiving payments. The login endpoint checks the verification status and returns 403 with an explanation.

Q2. How do you stop someone registering as an administrator?

The public register endpoint validates role with a Zod enum that allows only farmer and buyer. Staff accounts are created by an administrator. We fixed an earlier version that accepted any role.

Q3. What is the difference between authentication and authorisation here?

Authentication = Supabase checks email/password and issues a JWT. Authorisation = requireRole checks the role from the profiles table, and ownership helpers make sure a farmer only touches their own records.

Q4. Where do you validate and why in three places?

Frontend Zod for instant feedback; backend Zod middleware for security because the client can be bypassed; database constraints (NOT NULL, UNIQUE NIC, enums) for integrity. The server is the source of truth.

Q5. Explain the NIC validation.

Sri Lankan NIC has two formats: old = 9 digits followed by V or X (e.g. 781234567V), new = 12 digits. Regex: ^(\d{9}[VvXx]|\d{12})$. It is also UNIQUE in the database, so a duplicate returns 409.

Q6. How is the phone number validated?

Exactly 10 digits starting with 0: ^0\d{9}$, for example 0771234567.

Q7. What stops a farmer editing their own verification status?

The update endpoint copies only whitelisted columns (mass-assignment protection); verification status is not on the farmer whitelist and the status endpoint is restricted to officers/admins.

Q8. Can farmer A see farmer B's profile or crops?

No. Profile, crop, document and payment endpoints call an ownership check and return 403. The farmer list endpoint returns only the farmer's own row.

Q9. How does the language switch work and what if a translation is missing?

A React context stores the language in state and localStorage. t(key) returns the Sinhala/Tamil text or falls back to English, so nothing is blank.

Q10. How does the crop advisor decide?

Score out of 100 = location 40 + rotation 30 + soil pH 15 + rainfall 15. Each crop has pH and rainfall ranges and a crop family; district profiles hold rainfall and expert recommendations. We return the top 3 and show the per-factor breakdown.

Q11. Is it really AI / machine learning?

It is an explainable rule-based scoring engine. Optional Gemini only rewrites the explanation in the farmer's language; it never picks crops. A Weka/Java prototype was explored in ml-service. We chose a transparent model because farmers need reasons and we had no labelled training data.

Q12. Why is rotation important?

Growing the same crop or the same family repeatedly builds up pests and disease and depletes nutrients, while a legume after a cereal fixes nitrogen. Rotation violations are never recommended.

Q13. What happens if the farmer does not know their soil pH?

They choose "I don't know". The pH factor then gets a neutral score (9/15) and the note says pH was not provided.

Q14. How do you protect the advisor from abuse?

Login required, restricted to farmer/officer roles, 30 requests per 15 minutes, and strict input checks (district must exist, pH 3–10).

Q15. How are search strings made safe?

The search term goes through safeSearch() that removes the characters that have a meaning in a PostgREST filter and limits the length, preventing filter injection.

Q16. Why mask the bank account?

Least-privilege on sensitive data: only the last four digits are stored, enough for a farmer to recognise the account but useless to an attacker.

Q17. How are documents protected?

Private storage bucket, type and size checks, ownership checks and 10-minute signed links; staff can mark a document verified.

Q18. What would you improve next?

Real ML trained on historical yield data (the Weka prototype), email/SMS verification at registration, date validation for planting vs harvest, and soil test integration.

6. Know your limitations (answer honestly if asked)

  • The advisor is rule-based, not a trained model (see 2.6). Its district knowledge tables are written by hand and could be reviewed by an agricultural officer.
  • There is no email/phone confirmation at registration (accounts are created already confirmed); the officer verification step is the control.
  • The app keeps the access token in localStorage (common in SPAs, but exposed if the site had an XSS bug); helmet and input validation reduce that risk.
  • Registration also stores a bcrypt copy of the password hash in the profile table in addition to Supabase Auth – Supabase Auth remains the real credential store.
  • Automated tests (72 in total) cover the advisor scoring and all E1 validation rules (registration, farmer and crop formats, dates, soil pH); the screens themselves were checked manually.

8. Appendix – system foundations (same in every guide)

8.1 Architecture in one picture

Browser (React 18 + Vite + Tailwind + TanStack Query + react-hook-form + Zod) | HTTPS, JSON, header Authorization: Bearer <JWT> v Express REST API (Node.js + TypeScript) helmet · CORS · rate limit · authenticate · requireRole · validate(Zod) · controller · errorHandler | supabase-js (service-role key, server side only) v Supabase: PostgreSQL (tables, constraints, RPC functions, triggers) · Auth · Storage (private buckets)

Layered design: presentation (React pages) → API/business layer (Express controllers and services) → data layer (Supabase/PostgreSQL). Business rules that must never be bypassed (stock, weights, payments) are enforced in the database through PostgreSQL functions, so even a buggy client cannot break them.

8.2 Authentication vs authorisation

ConceptWhat it answersHow HarvestHub does it
Authentication"Who are you?"Email + password are checked by Supabase Auth. On success the API returns a JWT access token and a refresh token. The frontend stores them and the Axios interceptor adds Authorization: Bearer <token> to every request; on a 401 it tries the refresh token once, otherwise logs the user out.
Authorisation (RBAC)"What may you do?"authenticate middleware verifies the token with Supabase, loads the user's profiles row (role, account_status) and rejects suspended / inactive / pending accounts. requireRole(...) then allows only listed roles (administrator is a superuser). Wrong role → 403.
Ownership checks"Is this YOUR record?"Role alone is not enough: a farmer must not read another farmer's data. Controllers call helpers such as assertFarmerAccess / assertBuyerAccess (services/access.ts) → 403 if the record belongs to someone else.
Row Level Security (RLS)DB-level safety netPolicies are enabled on tables in Supabase. The API itself uses the service-role key, so the API-layer checks above are the primary control; RLS protects direct database access.

The nine roles are: farmer, collection_centre_officer, quality_inspector, inventory_manager, buyer, finance_officer, transport_coordinator, manager, administrator. Only farmer and buyer can self-register; staff accounts are created by an administrator.

8.5 Cross-cutting security measures

  • helmet security headers; CORS restricted to the configured frontend origin in production.
  • Rate limiting with express-rate-limit (general API and a stricter limit on /api/auth).
  • Safe search: user search text is stripped of characters that could alter a PostgREST filter (, ( ) % * \) and limited to 60 characters.
  • Mass-assignment protection: update endpoints copy only a whitelist of columns (a farmer cannot set their own verification status).
  • Generic login error ("Invalid email or password") so attackers cannot discover which emails exist.
  • Secrets only in .env (service-role key never reaches the browser); private storage buckets with short-lived signed URLs for documents.
  • Notifications and audit: important actions create in-app notification rows (and emails when SMTP is configured); auction awards and rejections are written to the audit log.
